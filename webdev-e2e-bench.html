§0 · 缘起

代码通过率回答不了「产品好不好用」

给 AI Coding 产品选模型，需要的是一把量「端到端交付体验」的尺子——而当时手里只有量「代码对不对」的。

项目的起点是一道方向修正题：最初的设想是 SWE-bench 式的补丁评测，但真实的产品问题是—— 给 AI Coding 产品选模型，需要知道的是模型交付的页面能不能用、好不好用，而不只是代码对不对。 2026-07-12，评测对象被重新定义为完整的 React/Vite/TypeScript 工程：从统一任务出发，驱动模型生成可运行的 Web 项目， 再对交付物做端到端检查。

传统代码评测以 pass@k 通过率为主：给定函数签名，跑测试用例，过与不过。这类信号对算法题有效， 却覆盖不了真实 Web 开发的决定性问题——页面能不能跑起来、视觉是否像产品、交互能不能闭环、 移动端是否可用、可访问性是否达标。模型在函数级评测里的高分，无法外推为「能交付一个好用的网页」。

2026 年 7 月起，先后调研了 19 个公开可核验的 Web 评测集合（15 个直接相关、4 个邻接对照，完整对比见 §3）后确认了这个盲区： 代码类基准止步于功能通过，网页类基准多停留在截图相似度或 E2E 测试通过，没有一把尺子同时量「能跑、好看、可用、健壮」—— 更没有人把「人工审美与产品体验」这种自动化最难啃的部分正式纳入评测。

调研对象量什么量不到什么
HumanEval / MBPP函数级代码生成（pass@k）页面、框架、工程环境、交互
SWE-bench 系真实 issue 修复（偏 Python）Web/全栈场景、视觉与体验
Web-Bench（字节）50 个 Web 项目 × 20 个顺序任务，E2E 测试 Pass@1视觉质量、交互自然度、人工审美
WebDev E2E Bench（本工作）端到端交付：功能 + 视觉 + 交互 + 响应式 + 可访问性 + 人工盲评——正是上面缺的那一块

这套体系服务三类决策者：AI 产品经理（不同模型适合哪些 Web 场景）、模型选型负责人（新版本是否值得切换）、 Agent 研发（低分到底来自模型还是工具链）。他们需要的不是一个分数，而是 「哪个模型、在哪个场景、为什么、下一步怎么办」。

三个设计决策（创新点）。① 评交付物而非代码片段：每个任务从统一 starter 出发，以可运行产品为终点； ② 6 类真实任务 × 7 个能力维度，把「做个网页」拆成可测量的格子； ③ 确定性 Auto + 双视觉 Judge + 人工盲评三把尺子交叉验证，先校准尺子、再量模型。 这三条在 §3 被扩展为五个可证明的创新点，并与 19 个竞品逐项对照。

§1 · 体系设计

把「做个网页」拆成可测量的 6 × 7

六类任务覆盖真实 Web 开发的主要场景，七个维度覆盖交付体验的完整切面——每个格子都有明确的归属尺子。

任务面：页面生成、功能实现、组件开发、页面改版、轻量全栈、Bugfix+UX——从「从零画一页」到「在存量代码里修体验」， 对应 AI Coding 产品的真实使用分布。维度面：功能正确性、端到端可用性、视觉质量、交互质量、响应式质量、可访问性、代码质量。

分工原则只有一条：能确定裁决的绝不用主观判断。功能契约、运行事实、可访问性规则交给确定性 Auto； 视觉与交互这类主观维度交给双视觉 Judge 独立打分；人工盲评只做校准与有效性检验（见 §12），不直接决定排名。 权重上对半开：自动化检查 50%，Judge/人工侧 50%——机器负责「事实」，人负责「感觉」，谁也不越界。

公平性靠工程约束保证：所有模型面对同一个干净 Starter、同一套工具与预算—— 30 回合 / 30 分钟 / 300K 输入 / 32K 输出 Token 四道闸门，超预算即冻结提交； 正式任务的隐藏测试、Judge rubric 与其他模型的结果对生成模型完全不可见； 生成与评估在固定 digest 的 Docker 镜像中执行，浏览器阻断一切非 localhost 请求。 效果分与成本、耗时等效率分严格分离，不允许「又快又便宜」稀释质量结论。

规模规划。体系按 6 题 Pilot → 30 题 V0.2 → 120 题 V1 → 500+ 分阶段扩展。 6 题 Pilot 已于 2026-08-14 冻结（六模型实测见 §6 起）；30 题 V0.2 集合于 2026-08-28 通过全部静态与运行门禁（见 §5）—— 先证明尺子在真实模型身上量得准（§7、§12），再谈放量。

§2 · 落地过程

从调研到 Pilot：一条全自动流水线

评测体系不是一份文档，而是一条跑起来的产线——以及一台看得见产线的控制台。

调研主流 Benchmark → 任务与维度设计 → 评估器开发与校准 → 可视化控制台 → 六模型 Pilot → 归因与迭代

从 2026-07-12 方案确立到 2026-08-14 正式冻结，共 34 天、11 个阶段，每一步都有明确的完成判断： 方案与指标体系（07-12）→ Evaluator Agent MVP（07-12）→ 中文可视化控制台（07-14）→ Generation Agent 与批量 Runner（08-12）→ 真实评测前审计与费用门禁（08-12）→ 六家模型接入与版本冻结（08-13）→ 评估器有效性校准（08-13）→ 协议消融与输出保护（08-13）→ 六模型正式 Pilot（08-14）→ 18 份人工盲评与归因诊断（08-14）→ 最终交付（08-14）。

真实调用 Token 之前先过审计：preflight 零成本检查模型冻结、密钥、Docker digest、浏览器与任务契约， 输出 GO 才允许开跑；费用账本逐次预留，硬止损 560 CNY。这套「先验证、再花钱」的纪律让 36 次正式生成 一次跑通，累计支出 ¥347.94，无一次返工重跑。

全流程落地为一条闭环产线：任务提交、模型生成、自动检查、双 Judge 评分、人工校准、结果分析， 标准评测的 11 个步骤中 10 个由系统完成（90.9%），审美与产品判断保留人工复核。 配套的可视化控制台与模型决策工作台支持实时查看 Pipeline 阶段、得分、三视口截图与问题详情。 按标准流程保守测算：单任务人工主动操作时间 42 → 12 分钟（−71.4%）， 报告整理时间 15 → 4 分钟（−73.3%）——人工的角色从「收集和整理」变为「复核和判断」。

口径声明。效率提升是按标准步骤的业务测算，不是已完成的正式对照实验； 评测规模、缺陷检出率与证据完整性（36/36 可追溯、34/36 三视口截图齐全）为实测数据。两者在本页严格分开表述。

提效的意义不只是省时间：评测量产之后，「每接一个模型就跑一轮」从周级工程变成日常操作， 评测从一次性项目变成可持续的产品基建。尺子本身的可信度在 §7 单独检验。

§3 · 竞品全景与创新点

19 个集合、五条赛道：差异不在某个指标，在闭环

「Web 评测」至少是五种不同的问题——操作既有网站、复刻截图、从需求生成、在项目中连续开发、判断结果好不好。 它们的输入、输出和成功标准不同，不能只用 Pass@1 或截图相似度横向比较。

2026-08-28 快照的 Benchmark Registry 收录了 19 个公开、可核验且与 Web 生成、编辑、前端工程或 Web 评判直接相关的集合 （15 个直接相关、4 个邻接对照），每项记录来源、成熟度与 12 类能力字段。按评测对象可以划成五条赛道—— 本项目聚焦的是其中没有被任何一条完整覆盖的问题：模型或 Coding Agent 能否把产品需求转化为可运行、可交互、 体验完整且可维护的 Web 产品，以及结果能否支持模型选型和产品优化。

把最接近的五项工作拉到同一张能力表上逐项对照，差异才说得清楚——「未作为核心维度」不等于相关项目完全没有对应检查， 而是其公开主要指标与报告目标并不以该维度为独立、稳定输出。这张表用于定位差异，不用于贬低其他集合。

五个可证明的创新点

① 从代码结果转向最终产品结果。评测对象是冻结后的可运行 Web 项目：构建成功只是入口， 之后还要完成浏览器用户流程、状态切换、多视口检查和体验评判——因此可以区分「代码能编译」和「产品真正可用」。

② 七维产品质量而非单一通过率。固定输出功能正确性、端到端可用性、视觉质量、交互质量、响应式、 可访问性和代码质量；七维权重沿用 V1.1，不通过改权重制造新成绩。

③ 评估器自身需要通过门禁。Gold、受控缺陷和重复运行用于验证确定性检出率、主观方向灵敏度和稳定性； 新集合的任务必须重新完成任务级 Gold 与负例验证，不能继承旧集合的结论（§5、§7）。

④ 把低分拆成可行动的根因。通过生成日志、工具协议、构建证据、浏览器证据和 Judge 分歧， 将问题归为模型能力、Agent 适配、基础设施或评估器——避免把工具协议失败误判为模型能力下降（§11、§15）。

⑤ 从排行榜转向产品决策。报告同时输出任务类型、难度、七维能力、失败模式、成本和可信度， 用于回答「哪个模型适合哪类场景」「版本是否达到上线门槛」「下一步应该优化模型还是 Agent」。

更准确的创新表述。这五条并非五个孤立的首创指标——单独看，每一条都有邻接工作沾边。 真正的差异是：把真实 Web 产品评测、自动与人工校准、评估器有效性验证、根因诊断和模型决策整合为一个端到端闭环。 闭环里的每一环都在本页有对应的章节与冻结证据。

§4 · 评测规范 V2.0

先把「怎么评」写成规范，再谈「评出了什么」

规范 V2.0 发布于 2026-08-28，适用于 V0.2 及后续集合——它回答的不是分数，而是：评的是什么、什么算一次有效运行、 隐藏测试能碰什么、分数怎么合成、什么时候允许改题。

评测单位是「一个模型/Agent 在固定预算内，针对一个公开任务契约，从干净 Starter 产生的冻结 Web 项目」—— 不是代码片段像不像参考答案，而是最终产品是否可运行、可交互、体验完整且可维护。 同一次结果必须绑定模型精确版本、Agent 协议、任务版本、Starter 哈希、Gold 哈希、测试哈希、评分版本、 运行环境、预算、提交哈希和证据路径，缺任何一项，结果不可入库。

规范把每一次运行明确归入五类状态，并规定只有两类计入模型结果——失败分类必须有日志或可复现实验证据， 不能根据分数主观归因：

运行状态定义是否计入模型结果
valid环境正常，模型在预算内产生可冻结提交计入
model_failure模型未完成、输出无效、主动破坏项目或耗尽预算计入，按门槛和实际证据评分
agent_failure工具协议或 Agent 解析器无法执行本可执行的动作不计入 —— 修复后诊断复测
infrastructure_failureAPI、网络、磁盘、浏览器或依赖服务故障不计入 —— 只允许受控重试
evaluator_failure测试或 Judge 本身错误、泄漏或不稳定不计入 —— 冻结结果并修正规则

公开契约与隐藏测试的边界是防泄题的核心：Prompt 公开目标用户、必须功能、状态、响应式和可访问性要求； 隐藏测试可依赖的稳定选择器写进 test_contract.stable_selectors 一并公开；每项必填功能必须能在 feature_checks 中追溯到至少一个检查。隐藏测试可以组合公开行为形成边界场景， 但不得检查未公开的功能、文案或 DOM 层级——任何隐藏检查使用了未披露的 selector、文本或业务规则，任务直接不得入库。 Gold 代表功能与状态的正确参考，不是要求模型复刻的视觉答案。

质量门槛：低分有地板，证据有纪律

安装或构建失败：端到端可用性上限 20、功能正确性上限 10；页面白屏或核心流程完全不可达：总分上限 40； 致命运行时错误阻断主流程：对应功能不得得分；缺少移动端核心流程：响应式不超过 50； 严重或致命 axe 问题按节点与影响扣分，键盘不可达的核心操作同时影响交互分。 LLM Judge 不得单独判定构建、功能或可访问性通过，也不得覆盖确定性失败； 双 Judge 任一维度分差超过 15 分即标记 disagreement，进入人工抽检池；无证据维度必须标记 unavailable，不能猜分。

难度不是感觉，是六项复杂度的加总

每题记录六项复杂度：页面/路由数量、核心交互步骤、可触发状态数量、数据依赖、错误分支、对既有功能的保持约束， 各按 0–2 分离散计分，总分 0–12：0–4 为 easy，5–8 为 medium，9–12 为 hard。 任务作者给出的难度必须经过 Gold 实跑与一名复核者确认；若模型批次出现明显天花板或地板效应， 只在下一集合版本调整，不原地改题。

公平性靠预算与冻结保证：相同模型矩阵使用同一双语需求、Starter、工具、环境和公开检查； 每次从干净项目启动，不得访问 Gold、隐藏测试、Judge rubric 或其他模型结果；模型精确版本冻结， 不使用无法解析的 latest；回合、时间、输入/输出 Token 和费用均设硬上限； 模型生成失败不得选择性重跑；主榜只比较质量，成本、耗时和 Token 单独报告。

版本关系（三层各自演进）。评分版本 V1.1：七维权重保持不变；规范版本 V2.0：新增任务元数据、失败分类、 契约边界和集合治理；集合版本 V0.2：30 题（§5），V0.1 六题与 2026-08-14 Pilot 永久保留。 冻结后的 Test 题不得原地修改，任何 Prompt、Gold、测试或 rubric 变化都必须提升版本，并保留桥接题用于新旧对比。 未来 V1：120 题，六类各 20 题，Dev/Validation/Test 为 30/30/60。

§5 · 任务集合 V0.2

从 6 题到 30 题：先证明题目可靠，再让模型上场

V0.1 的六类任务各只有一个样本，只能证明链路跑通；V0.2 把每一类扩展为 5 个产品变体， 并给整个集合加上「不通过就不许烧 Token」的质量门禁。

集合构成：六类任务各 5 题（页面生成、功能实现、组件开发、页面改版、轻量全栈、Bugfix+UX）， 难度 easy / medium / hard 各 10 题，按 Dev 12 / Validation 8 / Test 10 划分， 覆盖 SaaS 后台、电商、协作效率、内容社区、数据分析、服务运营 六个产品领域各 5 题—— 避免任务全部挤在 SaaS Dashboard 一个形态里。

任务生产方法：先由人工定义六个任务家族，再为每个家族构造五个产品变体——变体必须改变交互长度、 状态数量、数据依赖、页面数量或回归约束，不能只替换文案和颜色。每题交付双语需求、Starter、Gold、 公开契约、浏览器流程、人工 rubric、一个明显错误负例和一个 near-miss 负例； feature_checks 要求每项必填功能都能追溯到检查证据。静态覆盖度：30/30 题含多步骤交互与三视口/可访问性要求， 20 题声明至少四类状态，13 题含 Mock API 或外部数据依赖，10 题属于改版或回归修复，9 题含多页面/路由复杂度。

防泄漏按划分分层：Dev 公开任务、Starter、Gold 和测试，供 Agent 调试；Validation 公开任务与 Starter， 保留部分测试；Test 对外只提供任务与 Starter，Gold、隐藏测试和人工样例保存在私有评测环境。 每题记录来源、授权方式、变体组和污染风险；当前集合为内部专家设计，污染风险标记为 low—— 该标签表示未直接复制公开题面，不代表能证明训练数据中绝对不存在相似需求。

门禁真的拦住了问题：第一轮 16/30，修复后 30/30

第一轮运行门禁的结果是 Gold 16/30、负例 60/60、重复一致 30/30。失败没有被忽略、也没有靠降门槛消除， 而是按共享根因修复后整批重跑：

根因影响修复
筛选交互继承了上一步的搜索条件5 个功能实现任务的筛选断言失败筛选前恢复干净页面状态，确保每个行为独立可复现

第二轮结果：Gold 30/30、负例 60/60、重复一致 30/30。这个过程本身就是门禁价值的证明—— 它在消耗任何模型 Token 之前，先发现了任务和测试自身的 14 处问题。

门禁顺序与诚实边界。按规范，正式发布前还需抽取 20%（6 题）做独立人工需求歧义复核—— 由未参与出题的人检查目标用户、可执行性、多义性、selector 约束与难度合理性，且不能用作者自评代替。 复核通过并重跑门禁后，才执行 2 模型 × 6 代表题的低成本 Smoke Test；链路与区分度正常，才讨论正式实验。 V0.2 不新增付费模型成绩：它是任务集合与评估器的质量保证版本，不是又一轮排行榜。

§6 · 核心结论（Pilot）

第一梯队有两个名字，但统计上还不是一场胜负

36 个有效样本、三套相互独立的评分体系，给出的最强结论是一条谨慎的并列线。

在统一任务与 Agent 预算下，DeepSeek V4 Pro 以平均 Final Score 83.71 居首， ChatGPT/Codex GPT-5 参照组 83.30 紧随其后——两者相差 0.41 分， 而 95% Bootstrap 置信区间分别为 79.66–87.81 与 77.79–88.81，高度重叠。 6 个同任务配对中 DeepSeek 赢 4 次、ChatGPT/Codex 赢 2 次。 本轮只能判断二者处于第一梯队，不能声称存在统计显著的胜负。

Kimi K3（80.55）、ERNIE 5.1（79.43）与 Doubao Seed 2.1 Turbo（79.23）整体接近，但擅长的任务类型不同； Qwen 3.8 Max（68.84）在多数页面任务上并非全面落后，但单个复杂全栈任务的严重失败（工单 CRUD 仅 16.04 分） 显著拉低总分并扩大方差。本轮属于 Pilot，不应外推为通用模型权威排名。

评分构成。Final Score 由确定性自动化检查（Auto）与 Kimi/Qwen 双视觉 Judge 加权合成； 人工盲评 18/18 份已完成，但因单评审、任务抽样不均与分数区间压缩，只用于校准评估体系，不覆盖正式排名。

人工盲评：校准器，不是裁判

18 份匿名盲评隐藏了生成模型身份，同时提供任务需求、三端截图、交互证据与源码摘要。 人工均值最高的是 ChatGPT/Codex（89.67）与 Kimi（89.17），DeepSeek 88.00 排第四—— 但由于不同模型抽到的任务并不完全一致、且只有一名评审、人工分数集中在 82 至 91， 该表不能解释为人工模型排行榜。它真正的价值在 §12：检验自动分与 Judge 分各自离人的判断有多远。

§7 · 评测机制

先证明尺子可信，再用它量模型

正式实验之前，评估器先通过了一组比模型考试更苛刻的入学考试。

整条流水线是「模型生成 → 自动化评估 → 双 Judge → 人工校准 → 统计报告」的闭环。 生成端：统一 Generation Agent、统一 starter、统一预算；评估端：确定性检查覆盖功能契约与运行事实， 双视觉 Judge 补主观维度，人工盲评只做校准。评估器 v1.3b 在正式实验前完成全量校准并冻结—— 六项门禁全部达标，才有后面的 36 次生成。

即便如此，尺子仍有盲区：受控校准中评估器漏检了 weak-information-hierarchy 这一细微主观缺陷， 跨 Judge 最大维度分差达 20。这也是「LLM Judge 不能替代人工抽检」这一结论的直接依据—— 它不是谨慎的口号，而是被漏检案例钉死的事实。

从交付包到冻结榜单：一个月的关键节点

从 7 月 9 日的汇报交付包，到 8 月 13 日三项校准与修复报告，再到 8 月 14 日 36 样本正式冻结与 18 份人工盲评完成—— 下面是这台评测机器成形的时间线。

§8 · 总榜

0.41 分的差距，11 分的区间

排名表回答「谁在前面」，置信区间回答「这个前面有多稳」。

把 95% Bootstrap 区间画出来，榜首的叙事立刻改变：DeepSeek 的区间完全落在 ChatGPT/Codex 区间之内， Kimi、ERNIE、Doubao 三家区间彼此交叠，而 Qwen 的区间下限探到 46.48——那是工单 CRUD 单项 16.04 分拖出来的尾巴。 逐行点击可钻取每个模型的 Auto / Judge / Human 三层分与成本。

配对胜率提供了第二个视角：DeepSeek 对 Doubao、ERNIE、Qwen 均为 5:1（83.3%），对 ChatGPT/Codex 4:2， 对 Kimi 3:3 打平；Kimi 对 Doubao 5:1 是本轮最悬殊的一对。15 组配对全部基于 6 个同任务一一对比。

§9 · 分类能力

没有全能冠军：六个任务类别，四个不同的最佳

把总分拆成任务类别，「谁更强」立刻变成「谁在哪件事上更强」。

页面生成的最佳是 Kimi（91.54），页面改版的最佳是 ERNIE（93.81），而组件开发、轻量全栈与 Bugfix+UX 三个类别的最佳都是 DeepSeek。功能实现类别由 Kimi 以 79.42 领先，但幅度有限。 浅色格子里藏着本轮最重要的单项事实：Qwen 在轻量全栈（工单 CRUD）只得 16.04 分—— 一次 Agent 写入协议的灾难性失败，而非页面能力的普遍崩塌。

七维画像

把六个模型的七维评分并排展开，共同形状一目了然：端到端可用性普遍满分或接近满分—— 主路径都能跑通；五个国内模型的最弱维全部是交互质量，ChatGPT/Codex 的最弱维是可访问性（64.67）。 当前模型更容易完成静态结构与主路径，对细粒度状态契约、键盘体验和边界条件掌握不足。

§10 · 难度压力测试

难度上升时，谁的分数先松手

easy 档人人九十分上下，hard 档才见真章——降幅本身就是能力画像。

从 easy 到 hard，DeepSeek 只降 3.48 分，是六家中最稳的；ChatGPT/Codex 降 10.35 分； Qwen 降 36.36 分，主要受工单 CRUD 单项严重失败影响——这说明其本轮 Agent 执行稳定性不足， 而不是所有页面任务都弱。Kimi 在 easy 档最高（92.59）却在 medium 档跌到 69.71，是六家中唯一「中档塌陷」的曲线。

§11 · 失败解剖

483 条失败标签，将近四成写着同一个词：交互

模型能交出「看起来像产品」的页面，却常常在「用起来像产品」上失分。

六模型累计失败标签归一化后，交互问题 184 条高居第一，其次依次是可访问性（68）、需求契约（61）、 响应式（43）与代码质量（41）。最高频的单一标签是 missing_required_content（23 次）， 紧随其后的是 poor_code_maintainability（17）与 monolithic_component（16）—— 「能生成页面」不等于「代码适合继续维护」。

典型形态：筛选、分页、重试、Toast 或 Modal 状态能展示但无法完整闭环；loading、empty、error 边界状态缺失或不可触发； 移动端出现表格裁切、文本溢出、首要操作跌出首屏；对比度、控件可访问名称、焦点恢复与键盘操作是高频可访问性失分点。

§12 · 评估器有效性

三把尺子互相对表：相关，但谁也替代不了谁

自动分、双 Judge 分、人工分——两两 Spearman 相关系数画在同一根轴上，结论比任何单一数字都诚实。

自动化分与双 Judge 分相关 ρ=0.6191，中等正相关：关注点相关，但不可互相替代。 双 Judge 与人工评分 ρ=0.4599，弱到中等：Judge 有辅助价值，不能替代人工偏好。 自动化分与人工评分 ρ=−0.1180——当前人工样本少、任务不均衡且分数区间压缩， 不能据此认定自动化与人工偏好稳定负相关，只能标记为探索性信号。

同供应商 Judge 相对跨供应商 Judge 的平均偏差为 −0.18 分（n=12），本轮未观察到明显自评偏高。 评估器能定位 Qwen 工单 CRUD 的功能崩坏，也能区分「高自动分但交互、视觉与完成度一般」的结果—— 但结合人工数据，最终结论仍是：LLM Judge 不能替代人工盲评。

人工六维里也有一个数据缺陷值得留档：代码质量维度的 18 份评分全部为 85 分，零方差， 无法计算该维度的人机相关性——它同时说明，单评审的人工数据本身也需要更大的样本才有统计力气。

§13 · 成本与效率

最便宜的不是最差的，最贵的也不是最好的

质量–成本 Spearman ρ=−0.3498：花钱买分的方向是对的，但效率差异接近五倍。

五个 API 模型中，DeepSeek 与 ERNIE 的平均总成本同为 $0.31/任务，Qwen 达 $1.40/任务—— 质量榜的榜尾恰好是成本榜的榜首。Kimi 平均耗时 541.93 秒，约为 ERNIE（175.42 秒）的 3 倍。 ChatGPT/Codex 走订阅制外部 Agent，Token 与费用不可核验，已从成本比较中排除（图中以缺口标记，不插值）。

成本口径。本阶段累计记录支出 347.94 元（硬止损 560 元，剩余 212.06 元）， 包含前置接入、消融、失败恢复、正式生成与 Judge，不等同于 36 个最终样本的纯净边际成本； Doubao 与 Qwen 费用采用保守上界，成本结论仅作方向性参考。

§14 · 裁决

把证据放上秤：指针停在「并列第一梯队」

左盘是「DeepSeek 已显著领先」的证据，右盘是「尚不能声称胜负」的证据——虚线砝码是还没落地的升级信号。

秤的读数规则很简单：证据砝码落盘越多，梁往哪边倾。目前右盘更沉——差距太小、区间重叠、样本太少、 人工偏好甚至反向。底部红斜纹封条写着共同证伪条件：任何一条出现，整杆秤重称。 梁的倾角是定性示意，不是打分。

§15 · 闭环与下一步

闭环已经跑通过一次：归因 → 修复 → 复测

评测体系的终点不是一张榜单，而是让一次失败变成一次可验证的产品改进。

§11 的失败解剖把问题分成三类：模型能力、工具适配、运行环境。Qwen 工单 CRUD 的 16.04 分被归因为 工具适配——Agent 写入协议缺陷而非模型不会写页面。修复分块写入与写后验证协议后复测同一任务： 得分提升 53.03 分，输入 Token 降低 70.8%。按测量纪律，这次复测属于不计榜诊断， 正式分数保持冻结——但它的价值不在榜上：它证明了这套体系能定位问题、验证修复、量化收益。

四条路径，一张概率盘

从「本轮结论」到「可信榜单」之间，隔着四个必须按顺序跨过的台阶。 最优先的不是扩任务量，而是先把分块写入与写后验证做成所有模型共享的 Agent 能力—— Qwen 的不计榜诊断已证明它能显著改善完成率；然后对关键任务增加至少 2 次独立重复， 把 15.29 分量级的运行间方差从「排名噪声」变成「可报告的误差棒」。在这些条件满足之前， 不直接扩到 500 个任务，也不发布权威排行榜。
