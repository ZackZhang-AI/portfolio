§01

评测集怎么构造

DATASET

评测集是整个评测体系的地基——评测集偏了，后面所有指标都是错的。核心原则：让题目分布逼近真实使用分布，而不是随便凑几个问题。

1.1三种来源，三种用途

来源机制用途与风险
LLM 自动生成知识库采样文档 → 按题型生成 QA 对主路径。成本低可批量；风险是"模型给自己出题"，分布天然偏乐观
自定义上传JSON / CSV / xlsx 注入 question + ground_truth保真路径。混入真实用户 query，校正分布偏差
历史沉淀每轮 badcase 回收入库回归路径。形成越测越厚的 golden set，防止优化引入回归

实操建议：自动生成的题只构成"底集"，必须混入真实 query，比例从 8:2 起步，逐步向真实分布靠拢。

1.2题型配比是分布设计，不是随手填的

单跳问题SINGLE-HOP
70%
度量检索精度 + 抽取忠实度。失败含义：检索没命中，或生成时抄错。
多跳问题MULTI-HOP
20%
度量查询分解 + 跨段落综合。失败含义：多跳识别 / 子查询规划失败——本项目实测的薄弱环节。
错误陷阱题ERROR
10%
忠实度的压力测试。对"文中没有的信息"提问，专测拒答防线——10% 的陷阱题，产出整条防线的可信度信号。

配比原则：按线上真实 query 分布定基线，再对薄弱题型刻意加权。发现多跳弱，就临时提高 multi_hop 占比采集更多失败样本——这是"采样服务于归因"，不是刷指标。

1.3生成质量的三道闸

  1. 生成约束按题型切换 system prompt（陷阱题用"考官出题"人格），强制纯 JSON 输出，截断超长文本。
  2. 解析兜底JSON 解析失败即整批丢弃——带病数据不进库。
  3. 人工审校逐条过：问题是否具体、ground truth 是否可由原文支撑、题型标注是否正确。宁可删掉 30% 的题，也不让脏题进评测集——一条 ground truth 本身有错的题，会把噪音混进所有指标。
§02

指标怎么选

METRICS

选指标的原则：每个指标都要能回答一个"坏了该怎么办"的问题。答不上来的指标是虚荣指标。

2.1质量四维：一张分层归因坐标系

指标回答的问题低了怎么办
忠实度 / Faithfulness回答是否完全基于检索上下文？有无幻觉？收紧"仅基于上下文"约束，降温度
相关性 / Relevancy回答是否直接且完整解决了问题？引入查询重写 / 多跳分解
上下文精度 / Context Precision检索回来的片段与问题有多相关？调检索参数，上/调 Rerank
准确性 / Accuracy与 ground truth 的一致程度需参考答案才可评，作端到端校验

四维不是平行的：Context Precision 管检索层，Faithfulness / Relevancy 管生成层，Accuracy 管端到端。分数一出来，故障域就缩小了一半（见 §03）。

§03

Badcase 怎么归因

ATTRIBUTION

归因口诀：先定故障域，再定根因，最后才谈方案。上来就改 prompt，是最常见的错误。

3.1四层归因框架：拿到低分样本，按这个顺序排查

①
评判层JUDGE
judge 判得对吗？人工复核该条评分，judge 误判则记录为 judge badcase，不计入系统问题。
②
数据层DATA
题目本身对吗？ground truth 是否有原文支撑？题型标注对吗？脏题直接删题。
③
检索层RETRIEVAL
该检的检回来了吗？看 source_documents：答案所在 chunk 不在 top-k → 查 embedding、分块、Rerank。
④
生成层GENERATION
检对了但答错了吗？上下文里有答案却没用到 / 用错 → 归因 prompt、温度、生成约束。

多跳题额外一问：是分解失败（子查询没覆盖关键知识点）还是合成失败（子查询都对，最终答案没拼好）？前者归因查询规划，后者归因生成。陷阱题答错只有一种归因：拒答防线失效。

3.2指标联动归因：不用逐条看的快查表

分数模式归因方向
上下文精度低 + 忠实度低检索引入噪音 → 先修检索 / Rerank
上下文精度高 + 相关性低检索对了但答非所问 → 查询理解 / 生成指令
忠实度低（集中在陷阱题）拒答防线失效 → prompt 约束 + 拒答样本
准确性低但其余高judge 与 ground truth 表述差异 → 复核 judge（见 §04）

3.3Badcase 的归宿：入库，不是关掉

每个确认的 badcase 带归因标签（retrieval / generation / data / judge + 子类）沉淀进回归集：改动后重跑验证修复且无副作用；按归因类别统计占比变化，回答"这个季度的优化把哪类问题打下去了"。没有结构化归因标签的 badcase，只是被"看到"，没有被"管理"。

§04

人工标注 × LLM-as-Judge

HUMAN × JUDGE

4.1分工：机器管广度，人管准度

LLM / Judge 做

  • 评测集初稿：批量生成 QA 对
  • 全量打分：每条样本四维打分 + 理由
  • 初筛：把低分样本筛出来交人工

人工做

  • 评测集定稿：逐条审校、删脏题
  • 评分抽检：按比例复核，算人机一致率
  • 争议仲裁：低分样本逐条复核
  • 归因决策：打标签、定优化优先级

为什么不能全交给 judge：judge 与被测系统可能同源，存在"惺惺相惜"偏差；且 judge 对"答案对但表述不同"与"答案错但说得像"的区分能力有限。

4.2Judge 的可靠性工程

已做
结构化输出强制 JSON schema（scores + reasons + overall），正则兜底解析，失败标记 error 而非猜测。
已做
要求给理由reasons 不只是可解释性，更是人工抽检的抓手——复核先看理由是否成立，比重新打分快得多。
待做
人机一致率监控每轮固定抽 10–20% 人工打分，一致率 < 80% 时该轮指标不可信，先修 judge prompt 再谈系统优化。
待做
盲评与校准judge prompt 不透露 ground truth 来源防锚定；用已知好/中/差的锚定样本校准打分分布。
待做
多次采样取中位judge 有随机性，关键指标跑 2–3 次取中位数降方差。

4.3人工时间只花在三个刀刃上

  1. 评测集定稿一次性成本，长期复用。
  2. judge 抽检每轮 10–20%，监控一致率。
  3. 低分样本仲裁低分样本是信息密度最高的地方，逐条复核。

自动化评测的产出不是"不用人"，而是让人工注意力精确投放到信号最强的地方。

§05

工程化：评测作为流水线

PIPELINE

方法论要能跑在工程上才算闭环。项目实现形态：

0Pending→ 4DatasetGenerated→ 1Running→ 2Completed / 3Failed

数据集生成与评测执行是两个独立阶段——先把题审好，再开跑，避免"边生成边评"的不可控。

机制设计为什么
异步执行生成与评测走后台任务，进度可轮询前端实时展示，不阻塞交互
逐条落盘每评一条立即写库，单条失败记 error_msg坏样本不拖垮整轮评测
报告双写Markdown 落盘 + API 可取支持前端展示与跨轮归档比对

这套设计支撑的朴素诉求：评测要像单元测试一样，改完代码随手就能跑一轮，且结果可比对。

§06

局限与迭代路线

ROADMAP
现状局限风险下一步
judge 与被测系统可能同源打分偏高、风格偏袒异构 judge + 人机一致率监控
缺一致率指标无法证明 judge 可信固定抽检比例，出 Kappa 报告
小样本场景（n=2 的多跳）分数无统计意义扩大薄弱题型采样，报告标注置信度
自动生成题偏模型分布评测偏乐观混入线上真实 query，8:2 → 5:5
badcase 无结构化归因标签只被看到没被管理归因标签入库 + 回归集
未接入标准框架对外可比性弱对齐 RAGAS 指标口径做交叉验证
